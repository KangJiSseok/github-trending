# GIT-7 Design

## Source of truth

- Linear issue `GIT-7`: add PostgreSQL, Prisma schema, and local DB runtime
- Workspace conventions established by `GIT-1`

## Goal

Create the smallest database foundation that lets later persistence and read-layer issues run against a real local PostgreSQL instance without forcing DB concerns into the app packages yet.

## Chosen approach

Use a package-owned database workspace at `packages/db`.

- `packages/db` owns the Prisma schema, generated client, package scripts, and package-level tests.
- The repo root owns only operator-facing setup files: `.env.example`, `docker-compose.yml`, and README instructions.
- App packages stay unchanged unless they later need to consume `@repo/db`.

## Why this cut

This matches the issue scope and the repo's current monorepo shape:

- `packages/config` already establishes the shared-package pattern to mirror.
- `pnpm-workspace.yaml` already includes `packages/*`.
- Root scripts already use recursive `--if-present` execution.
- There is no existing env, Docker, or database runtime to unwind.

Keeping Prisma at the package boundary avoids mixing generated artifacts, schema ownership, and migration commands into the repo root or app packages.

## Files in scope

### Root

- `package.json`
- `README.md`
- `.env.example`
- `docker-compose.yml`

### Database package

- `packages/db/package.json`
- `packages/db/tsconfig.json`
- `packages/db/vitest.config.ts`
- `packages/db/prisma.config.ts`
- `packages/db/prisma/schema.prisma`
- `packages/db/src/client.ts`
- `packages/db/src/index.ts`
- `packages/db/src/client.test.ts`

## DB package contract

`@repo/db` should export a small Prisma client boundary for later worker and read-model code.

- `createPrismaClient()` returns a configured `PrismaClient` instance.
- The generated Prisma client lives under `packages/db/generated/client` so the package owns its artifacts explicitly.
- Package scripts expose local developer commands for generate and migrate flows.

## Schema contract

The first schema cut includes only the tables explicitly named in the issue:

- `repositories`
- `raw_events`
- `repository_daily_metrics`
- `repository_weekly_metrics`
- `keyword_daily_metrics`
- `generated_summaries`
- `ingestion_runs`

The schema should include the minimum uniqueness and foreign-key constraints needed to prevent duplicate event ingestion and support later daily/weekly aggregations.

## Local runtime contract

- `docker-compose.yml` runs one local PostgreSQL service with a healthcheck.
- `.env.example` defines one local `DATABASE_URL` and matching `DIRECT_URL`.
- local setup explicitly copies `.env.example` to a root `.env` before Prisma commands run.
- README adds the exact bring-up and migration commands for local development.

## Testing strategy

- Start with a failing package-level test for the exported Prisma client boundary.
- Keep the test small: verify `createPrismaClient()` returns a client instance with the expected configuration surface.
- Use the issue verification commands to prove the local runtime, migration flow, client generation, and package tests all work together.

## Explicit deferrals

The following are intentionally out of scope for GIT-7:

- worker ingestion implementation
- repository/query layer code
- app-level DB consumption
- CI database services
- production deployment/runtime configuration

## Risks to watch

- Prisma env lookup can get confusing if URLs are duplicated across multiple `.env` files.
- Prisma v7 no longer guarantees `migrate dev` also generates a fresh client, so generate should remain explicit.
- Generated client output must stay inside the package boundary so later imports are stable.
